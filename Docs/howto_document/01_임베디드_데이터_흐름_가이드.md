## 1. 왜 데이터 흐름이 중요한가

임베디드 시스템의 버그는 대부분 두 가지 중 하나입니다.

- **타이밍 문제**: 언제 실행되는가
- **데이터 문제**: 어떤 값이 어디서 어디로 흘러가는가

후자가 생각보다 훨씬 많습니다. 특히 아래 상황에서 데이터 흐름이 불명확하면 디버깅에 수십 시간이 걸립니다.

- 센서값이 어느 단계에서 잘못된 값으로 변환되는지 모를 때
- 전역변수가 어디서 바뀌는지 추적이 안 될 때
- 여러 태스크가 같은 버퍼를 건드릴 때
- 단위가 섞여서 (mV인지 V인지, raw인지 calibrated인지) 혼란이 생길 때

데이터 흐름을 명확히 설계하고 문서화해두면, 버그가 생겼을 때 "어느 계층에서 이상이 생겼는가"를 빠르게 좁힐 수 있습니다.

## 2. 코딩 전에 흐름을 먼저 그린다

숙련된 개발자일수록 코딩보다 설계에 시간을 더 씁니다. 구현 전에 데이터가 어디서 시작해서 어디서 끝나는지 종이나 화이트보드에 먼저 그려봅니다.

이 과정이 중요한 이유는 두 가지입니다. 설계의 허점을 코딩 전에 발견할 수 있고, 이후에 쓰는 주석과 문서의 뼈대가 됩니다.

그릴 때 아래 질문을 스스로에게 던져보세요.

```
- 데이터의 출처는 어디인가? (센서, UART, Flash, 외부 명령 등)
- 어떤 변환/처리 단계를 거치는가?
- 최종적으로 어디서 소비되는가? (출력, 저장, 전송 등)
- 오류가 발생하면 어느 단계에서 어떻게 처리되는가?
```

**간단한 예시 — ADC 센서값 처리**

```
[하드웨어]
ADC 핀 (GPIO)
        ↓ raw 12bit 값 (0~4095)
[드라이버 계층]
sensor_adc_read()
        ↓ mV로 변환 (0~3300)
[처리 계층]
sensor_calibrate()
        ↓ 실제 물리량 (예: 온도 °C)
[응용 계층]
control_logic()
        ↓ 제어 신호
[출력]
GPIO / MQTT / UART
```

이 그림 하나가 이후 함수 설계, 주석, 테스트 케이스의 기준이 됩니다.

## 3. 계층 구조로 생각한다

임베디드 소프트웨어는 보통 아래 4개 계층으로 나뉩니다. 이 구조를 의식하면서 코드를 짜면 자연스럽게 데이터 흐름이 명확해집니다.

```
┌─────────────────────────────┐
│       응용 계층 (App)        │  판단, 제어 로직
├─────────────────────────────┤
│       처리 계층 (Logic)      │  필터링, 변환, 단위 환산
├─────────────────────────────┤
│       드라이버 계층 (Driver) │  하드웨어 추상화, raw 데이터
├─────────────────────────────┤
│       하드웨어 (HW)          │  센서, 액추에이터, 통신
└─────────────────────────────┘
```

**계층 간 규칙**

- 데이터는 **위로만** 올라갑니다. 드라이버가 응용 계층의 함수를 직접 호출하면 의존성이 꼬입니다.
- 각 계층은 **바로 아래 계층하고만** 통신합니다. 드라이버가 응용 계층을 알 필요가 없습니다.
- 계층 경계를 넘을 때 **타입이나 구조체로 인터페이스를 명확히** 합니다.

이 규칙을 어기면 나중에 코드를 재사용하거나 테스트하기가 어려워집니다.

## 4. 데이터의 소유권을 명확히 한다

경력자들이 공통적으로 강조하는 개념입니다. **어떤 모듈이 데이터를 만들고, 어떤 모듈이 소비하는지** 경계를 명확히 합니다.

```
sensor.c     → 데이터를 만드는 곳 (생산자)
filter.c     → 데이터를 가공하는 곳 (변환자)
mqtt.c       → 데이터를 소비하는 곳 (소비자)
```

소유권이 불명확할 때 나타나는 증상들입니다.

- 전역변수를 여러 파일에서 직접 읽고 씁니다.
- 같은 데이터를 여러 함수가 각자 다른 방식으로 변환합니다.
- 어디서 값이 바뀌었는지 추적할 수 없습니다.

**전역변수를 최소화하는 실천법**

전역변수는 반드시 필요한 경우에만 씁니다. 대신 함수의 파라미터와 반환값으로 데이터를 명시적으로 전달합니다.

```c
/* 나쁜 예 — 전역변수로 암묵적 공유 */
int g_temperature;  // 어디서든 바꿀 수 있음

void sensor_read(void) {
    g_temperature = adc_to_celsius(adc_read());
}

/* 좋은 예 — 함수 반환값으로 명시적 전달 */
esp_err_t sensor_read(int32_t *out_celsius) {
    adc_raw_t raw = adc_read();
    *out_celsius = adc_to_celsius(raw);
    return ESP_OK;
}
```

## 5. 타입과 단위로 경계를 표현한다

데이터가 계층을 넘어갈 때 타입과 단위가 바뀌는 지점이 버그의 온상입니다. 경력자들은 이 경계를 `typedef`와 구조체로 명시적으로 표현합니다.

```c
/* raw ADC값과 변환된 값을 타입으로 구분 */
typedef uint16_t adc_raw_t;    /**< ADC 원시값 (0 ~ 4095, 12bit) */
typedef int32_t  millivolts_t; /**< 변환된 전압값 (mV 단위) */
typedef float    celsius_t;    /**< 섭씨 온도 */

/* 함수 시그니처만 봐도 무슨 값이 들어오고 나가는지 명확 */
millivolts_t adc_to_mv(adc_raw_t raw);
celsius_t    mv_to_celsius(millivolts_t mv);
```

이렇게 하면 컴파일러가 타입 불일치를 잡아주고, 주석 없이도 함수의 입출력이 명확해집니다.

**단위를 변수명에 포함하는 습관**

타입 구분이 어려운 경우에는 변수명에 단위를 포함합니다.

```c
/* 단위가 불명확한 변수명 */
int temperature;
int voltage;

/* 단위가 명확한 변수명 */
int temperature_celsius;
int voltage_mv;
uint16_t adc_raw;
```

## 6. FreeRTOS 환경 — 태스크 간 흐름

FreeRTOS를 쓰는 ESP-IDF 환경에서는 함수 호출 관계보다 **태스크 간 Queue/Semaphore 흐름**이 더 중요합니다. Doxygen Call graph로는 이 흐름이 보이지 않습니다.

**태스크 간 데이터 흐름 예시**

```
sensor_task
    │  xQueueSend(sensor_queue, &raw_data)
    ▼
processing_task
    │  xQueueReceive(sensor_queue, &raw_data)
    │  처리 후
    │  xQueueSend(output_queue, &result)
    ▼
mqtt_task
    │  xQueueReceive(output_queue, &result)
    ▼
  mqtt_publish()
```

**태스크 설계 시 지켜야 할 것들**

데이터를 Queue로 전달할 때는 포인터 대신 **값을 복사해서 전달**합니다. 포인터를 전달하면 송신 태스크의 스택이 해제된 후 수신 태스크가 잘못된 메모리를 읽는 문제가 생깁니다.

```c
/* 나쁜 예 — 스택 포인터 전달 */
sensor_data_t data = { .temp = 25 };
xQueueSend(queue, &data, 0);  // data가 스택에 있으면 위험

/* 좋은 예 — 구조체 값 복사 전달 */
sensor_data_t data = { .temp = 25 };
xQueueSend(queue, &data, portMAX_DELAY);  // Queue가 내부적으로 복사
```

Queue 크기와 대기 시간(`portMAX_DELAY` vs 타임아웃)은 시스템 응답성에 직접 영향을 줍니다. 설계 초기에 각 Queue의 크기와 정책을 결정하고 주석으로 남겨두세요.

```c
/** @brief 센서 데이터 Queue
 *  @note  최대 10개 버퍼링. 처리 태스크가 10개 이상 밀리면 oldest 데이터 폐기.
 */
#define SENSOR_QUEUE_SIZE  10
```

## 7. 주석에 담아야 할 것과 담지 않아도 되는 것

코드만 읽으면 알 수 있는 것은 주석으로 쓰지 않습니다. 코드만으로는 알 수 없는 것, 즉 **설계 의도와 데이터의 의미**를 씁니다.

### 담지 않아도 되는 것

```c
/* 나쁜 주석 — 코드를 그대로 반복 */
i++;  // i를 1 증가시킨다

/* 나쁜 주석 — 너무 당연한 설명 */
// sensor_init을 호출한다
sensor_init();
```

### 반드시 담아야 할 것

**데이터의 의미와 단위**

```c
// ADC raw값(0~4095)을 mV로 환산. 기준전압 3300mV, 12bit 해상도.
int mv = (raw * 3300) / 4096;
```

**설계 의도 — 왜 이렇게 했는가**

```c
// DHT22는 연속 호출 시 최소 2초 간격 필요 (센서 스펙).
// 더 짧은 간격으로 호출하면 읽기 실패 반환.
vTaskDelay(pdMS_TO_TICKS(2000));
```

**하드웨어 제약**

```c
// ADC2는 Wi-Fi 활성화 시 사용 불가 (Espressif 기술 노트 참조).
// 반드시 ADC1만 사용할 것.
```

**비직관적인 알고리즘 선택 이유**

```c
// 이동평균 대신 중앙값 필터 사용.
// 이유: 진동 환경에서 순간적인 스파이크값이 많아 이동평균이 오염됨.
```

**미완성이거나 알려진 문제**

```c
// TODO: 현재 단순 평균. 가중 이동평균으로 교체 예정.
// BUG: 온도 -10°C 이하에서 변환 공식이 부정확함 (원인 미파악).
```

## 8. 현재 문서화 시스템과 연결하기

앞서 설명한 방법론을 현재 문서화 시스템에 대입하면 역할이 자연스럽게 나뉩니다.

| 데이터 흐름 관련 내용 | 어디에 담는가 | 태그/방법 |
|---|---|---|
| 전체 시스템 아키텍처 흐름도 | `Docs/mainpage.dox` | `\dot` (Graphviz) |
| 태스크 간 Queue 흐름 | `Docs/rtos_architecture.dox` | `@page` + `\dot` (Graphviz) |
| 함수 단위 처리 흐름 | `.c` 파일 함수 주석 | `@details` + `\dot` (Graphviz) |
| 데이터 타입과 단위 | `.h` 파일 typedef/구조체 | `/**<` 멤버 주석 |
| 함수 호출 관계 | 자동 생성 | Doxygen Call graph |
| 하드웨어 제약, 단위 | `.h` 파일 함수 주석 | `@note`, `@warning` |
| 알려진 버그, TODO | `.h` / `.c` 파일 주석 | `@bug`, `@todo` |

### 8.1 Graphviz (`\dot`) 다이어그램 작성법

Doxygen은 주석 내에 작성된 `\dot` ~ `\enddot` 블록을 자동으로 인식하여 다이어그램 이미지로 변환합니다. 별도의 이미지 툴을 사용할 필요 없이 코드 수정과 함께 다이어그램을 쉽게 관리할 수 있습니다.

**기본 문법 및 예시:**

```c
/**
 * @brief 센서 데이터 처리 과정
 * 
 * @details 아래는 ADC 센서 값이 어떻게 가공되는지 보여주는 데이터 흐름도입니다.
 * 
 * \dot
 * digraph DataFlow {
 *     // 1. 노드(박스) 스타일 설정
 *     node [shape=box, fontname="Helvetica", fontsize=10];
 *     edge [fontname="Helvetica", fontsize=9];
 * 
 *     // 2. 구성 요소(노드) 정의
 *     HW_ADC   [label="HW: ADC 핀", style=filled, fillcolor=lightgray];
 *     Driver   [label="Driver: sensor_adc_read()"];
 *     Logic    [label="Logic: sensor_calibrate()"];
 *     App      [label="App: control_logic()"];
 *     
 *     // 3. 흐름(화살표) 연결 및 라벨 작성
 *     HW_ADC -> Driver [label=" Raw 12bit (0~4095)"];
 *     Driver -> Logic  [label=" Voltage (mV)"];
 *     Logic -> App     [label=" Temp (°C)"];
 * }
 * \enddot
 */
```

**작성 팁:**
1. **`digraph` 이름:** 다이어그램마다 고유한 이름(예: `DataFlow`)을 지정해야 합니다.
2. **`node [shape=box]`:** 노드를 기본 타원형 대신 사각형으로 만들어 가독성을 높입니다.
3. **`->` 연결:** `A -> B` 형태로 데이터를 전달하는 방향을 직관적으로 표현합니다.
4. **`[label="..."]`:** 화살표 옆에 전달되는 데이터의 타입과 단위(예: `Voltage (mV)`)를 반드시 명시하세요.

## 9. 실전 체크리스트

새 모듈이나 함수를 설계할 때 아래 항목을 순서대로 확인합니다.

**설계 단계 (코딩 전)**

- [ ] 이 모듈에 들어오는 데이터의 출처와 타입을 정의했는가
- [ ] 이 모듈에서 나가는 데이터의 목적지와 타입을 정의했는가
- [ ] 계층 규칙을 지키는가 (위 계층에 의존하지 않는가)
- [ ] 데이터 소유권이 명확한가 (생산자/소비자 구분)
- [ ] 오류 발생 시 데이터 흐름이 어떻게 되는가

**구현 단계**

- [ ] 전역변수 없이 파라미터/반환값으로 데이터를 전달하는가
- [ ] 계층 경계에서 타입과 단위가 명확히 구분되는가
- [ ] FreeRTOS Queue를 쓴다면 포인터 대신 값을 복사하는가

**주석 작성 단계 (구현 직후)**

- [ ] 데이터의 단위와 범위를 주석에 명시했는가
- [ ] 비직관적인 선택의 이유를 설명했는가
- [ ] 하드웨어 제약사항을 `@note` 또는 `@warning`으로 남겼는가
- [ ] 알려진 문제나 미완성 부분을 `@bug` / `@todo`로 기록했는가
- [ ] 복잡한 흐름이 있다면 `@details`에 Graphviz(`\dot`) 흐름도를 추가했는가
