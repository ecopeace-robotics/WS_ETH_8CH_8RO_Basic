## 1. 이 시스템이 무엇인가

코드를 작성하면서 남기는 **주석이 곧 문서가 되는 파이프라인**입니다.

개발자는 함수와 파일에 정해진 규칙대로 주석을 답니다. 이후 스크립트 하나를 실행하면 함수 관계도, 파라미터 표, 데이터 흐름도가 포함된 HTML 문서가 자동으로 생성됩니다. 별도의 문서 작업 없이 코드와 문서가 항상 같은 상태를 유지하는 것이 핵심 목표입니다.

```
주석 작성  →  스크립트 실행 한 번  →  HTML 문서 자동 생성
```

**이 시스템이 해결하는 문제**

- 코드는 있는데 문서가 없어서 팀원이 이해하는 데 시간이 걸리는 상황
- 문서를 별도로 작성했지만 코드가 바뀌면서 문서가 낡아버리는 상황
- 새 프로젝트를 시작할 때마다 문서 구조를 처음부터 다시 고민하는 상황

## 2. 적합한 환경과 한계

### 적합한 환경

| 항목 | 내용 |
|---|---|
| 언어 | **C / C++** |
| 프레임워크 | ESP-IDF, Arduino, STM32 HAL, 순수 C/C++ 등 **C/C++ 기반이면 모두 적용 가능** |
| 개발 OS | **Ubuntu** (Linux 계열) |
| 버전 관리 | **Git** |
| 에디터 | VSCode 권장 (필수는 아님) |

프레임워크에 따라 바뀌는 것은 소스 폴더 경로, 빌드 명령어, 제외 경로 정도입니다. Doxygen 주석 문법, Doxyfile 구조, 스크립트 로직은 **프레임워크와 무관하게 동일**합니다. 자세한 내용은 [7장 프레임워크별 적용 가이드](#7-프레임워크별-적용-가이드)를 참조하세요.

### 한계 — 이런 경우에는 맞지 않습니다

**언어 측면**

Doxygen은 C/C++ 전용 도구입니다. Python, JavaScript, Rust 등 다른 언어 프로젝트에는 각 언어에 맞는 별도 도구(Sphinx, JSDoc, rustdoc 등)가 더 적합합니다.

**프로젝트 규모 측면**

파일이 수백 개를 넘어가는 대형 프로젝트에서는 Doxygen 실행 시간이 길어지고 HTML 출력이 복잡해집니다. 이 시스템은 **소규모~중규모 팀 내부 프로젝트**를 주요 대상으로 설계되었습니다.

**문서 공개 측면**

이 시스템은 **팀 내부 문서화**를 목표로 합니다. GitHub Pages를 통한 외부 공개나 대외용 API 문서 배포를 주목적으로 한다면 추가 설정이 필요합니다.

**자동화 측면**

문서 생성(`generate_docs.sh`)은 개발자가 직접 실행해야 합니다. CI/CD 파이프라인과의 연동은 이 시스템의 범위 밖입니다.

## 3. 전체 구조 한눈에 보기

### 파이프라인

```
[코드 작성]                [문서화 설정]
    │                           │
    ▼                           ▼
.h / .c 주석 작성          Doxyfile 설정
(Doxygen 표준 태그)        Docs/mainpage.dox 작성
    │                           │
    └──────────┬────────────────┘
               ▼
       generate_docs.sh 실행
               │
       ┌───────┴────────┐
       ▼                ▼
  VERSION 파일      Doxygen 실행
  버전 자동 주입    main/ + Docs/ 파싱
       │                │
       └───────┬────────┘
               ▼
    docs/doxygen/html/index.html
               │
       ┌───────┴────────┐
       ▼                ▼
   브라우저에서       doxygen_warnings.log
   HTML 확인         누락 주석 확인
```

### 개발 중 산출물과 역할

개발 과정에서 생성되는 주요 산출물과 그 역할을 정리했습니다.

#### 1단계: 코드 주석 작성 (개발자 책임)

| 산출물 | 위치 | 역할 | 작성 시점 |
|---|---|---|---|
| **파일 헤더 주석** | `.h`, `.c` 상단 | 파일의 목적, 관련 모듈, 구현 세부사항 | 파일 생성 시 |
| **API 명세 주석** | `.h`의 함수 선언 위 | 함수의 목적, 파라미터, 반환값, 에러 조건 | 함수 설계 시 |
| **구현 설명 주석** | `.c`의 함수 구현 위 | 복잡한 알고리즘, Graphviz 흐름도, 주의사항 | 복잡 로직 구현 시 |
| **구조체/열거형 주석** | 타입 정의 위 | 멤버의 의미, 초기값, 유효 범위 | 타입 정의 시 |

**역할:** 개발자가 작성한 주석은 코드와 함께 Git에 저장되므로 코드 변경 시 주석도 함께 관리됩니다. 팀원이 함수를 사용할 때 `.h`의 주석을 보고 API 사용법을 이해합니다.

---

#### 2단계: 문서 생성 설정 (프로젝트 초기 1회)

| 산출물 | 역할 |
|---|---|
| **Doxyfile** | Doxygen에게 어느 폴더를 파싱할지, HTML을 어디에 생성할지 지시 |
| **Docs/mainpage.dox** | HTML 문서의 표지(Main Page) 정의 (프로젝트 소개, 모듈 목차) |
| **VERSION 파일** | 현재 버전 번호 기록 (릴리즈 시 수정) |
| **generate_docs.sh** | 위 설정을 이용해 Doxygen을 자동으로 실행하는 편의 스크립트 |

**역할:** 이 파일들은 문서 자동 생성의 기초입니다. 한 번 설정하면 개발자는 이후 `generate_docs.sh` 한 줄만 실행하면 됩니다.

---

#### 3단계: 문서 자동 생성 (개발자가 필요할 때 실행)

```bash
./generate_docs.sh
```

이 명령은 다음을 수행합니다:

1. **Doxygen 실행**
   - `main/`과 `Docs/` 폴더의 모든 주석을 파싱
   - 함수 관계도, Call graph, 상속 다이어그램 자동 생성
   - `VERSION` 파일의 버전 번호를 HTML 헤더에 자동 주입

2. **HTML 문서 생성**
   - `docs/doxygen/html/index.html` — 브라우저에서 열 수 있는 정적 HTML 문서
   - 포함 내용:
     - **Main Page** — `mainpage.dox`에서 정의한 표지
     - **Files** — 모든 소스파일 목록 및 파일별 함수 목록
     - **Modules** — `@defgroup`으로 그룹화된 모듈별 API 정리
     - **Classes/Structs** — 구조체 멤버 및 enum 목록
     - **Search** — 함수명, 파일명 검색 기능

3. **경고 로그 생성**
   - `doxygen_warnings.log` — 누락된 주석, 잘못된 태그 사용 등을 기록
   - 팀원이 주석의 품질을 점검하는 체크리스트로 사용

| 출력물 | 용도 |
|---|---|
| **HTML 문서** | 팀원이 API를 학습하고 참조하는 공식 레퍼런스 |
| **경고 로그** | "어떤 파일의 어느 줄에 주석이 빠졌는가"를 파악하고 개선 |

**중요:** HTML 문서는 자동 생성 산물이므로 직접 수정하면 안 됩니다. 수정이 필요하면 소스 주석을 먼저 수정한 후 다시 문서를 생성해야 합니다.

---

#### 4단계: 팀원의 문서 활용

개발자가 생성한 HTML 문서는 다음과 같이 활용됩니다:

- **새 팀원의 온보딩:** "이 프로젝트의 모든 API가 무엇인가?"를 한눈에 파악
- **다른 모듈 사용할 때:** 함수의 파라미터, 반환값, 에러 조건을 문서에서 확인
- **모듈 간 의존성 파악:** 함수의 Call graph를 보고 "이 함수를 호출하는 다른 함수는?"을 추적
- **코드 리뷰:** "이 함수가 공용 API인가, 내부 함수인가?"를 구분

## 5. 표준 개발 프로세스

### 5.1 새 프로젝트 시작

> 참조 문서: `Doxyfile_설정_가이드.md`, `mainpage_dox_가이드.md`, `README_template.md`
> 프레임워크에 따른 경로 설정은 이 문서 [3장](#3-프레임워크별-적용-가이드)을 먼저 확인하세요.

**① 기본 파일 배치**

```bash
# 버전 파일 생성
echo "1.0.0" > VERSION

# 문서 폴더 생성
mkdir -p Docs

# 스크립트 실행 권한 부여
chmod +x generate_docs.sh
```

**② Doxyfile 작성**

`Doxyfile_설정_가이드.md`의 최소 설정을 기준으로 아래 항목만 프로젝트에 맞게 수정합니다.

```ini
PROJECT_NAME    = "실제 프로젝트 이름"
PROJECT_BRIEF   = "20~40자 목적 중심 한 줄 설명"
INPUT           = main/ Docs/
```

**③ mainpage.dox 작성**

`mainpage_dox_가이드.md`의 최소 버전을 기준으로 작성합니다.
처음에는 소개, 하드웨어, 빌드 방법 세 섹션만으로 시작합니다.

**④ README.md 작성**

`README_template.md`를 복사해서 프로젝트에 맞게 채웁니다.
이 시점에 반드시 작성해야 할 항목은 소개, 하드웨어 목록, 결선도, ESP-IDF 버전입니다.

**⑤ .gitignore 설정 및 최초 커밋**

```bash
git add VERSION Doxyfile generate_docs.sh README.md .gitignore Docs/
git commit -m "docs: 문서화 시스템 초기 설정"
```

### 5.2 개발 진행 중

> 참조 문서: `Doxygen_주석_작성_표준.md`

**함수 하나를 완성할 때마다**

`.h` 파일에 API 명세 주석을 작성합니다. 복잡한 로직이 있는 함수라면 `.c` 파일에 Graphviz(`\dot`) 흐름도를 추가합니다.

```
우선순위
1. 파일 헤더 (@file, @brief) — 모든 .c / .h 파일
2. app_main()
3. 공용 함수 (.h에 선언된 것들)
4. 구조체 / 열거형
5. static 함수 (여유 있을 때)
```

**커밋 전 체크리스트 확인**

`Doxygen_주석_작성_표준.md` 10장의 커밋 전 체크리스트를 확인합니다.

**새 모듈이 생길 때**

`mainpage.dox`에 `@ref`로 해당 모듈 링크를 추가합니다.
별도 페이지가 필요하면 `Docs/`에 `.dox` 파일을 추가하고 `mainpage.dox`에 `@subpage`로 연결합니다.

### 5.3 문서 생성

필요할 때마다 실행합니다.

```bash
# 문서 생성
./generate_docs.sh

# 생성 후 브라우저 자동으로 열기
./generate_docs.sh --open
```

**실행 후 확인 순서**

```
1. 브라우저에서 Main Page 내용 확인
2. Files 섹션에서 전체 소스파일 목록 확인
3. 주요 함수에 Call graph 표시 여부 확인
4. doxygen_warnings.log 열어 누락 주석 확인
```

**경고 로그 활용**

```bash
cat doxygen_warnings.log
```

파일명과 줄 번호가 함께 출력되므로 그대로 따라가며 주석을 보완합니다. 경고가 없으면 로그 파일이 자동으로 삭제됩니다.

### 5.4 릴리즈

**① VERSION 파일 수정**

```bash
echo "1.1.0" > VERSION
```

버전 번호 규칙 (Semantic Versioning):

```
1  .  1  .  0
↑     ↑     ↑
MAJOR MINOR PATCH

PATCH → 버그 수정
MINOR → 기능 추가, 하위 호환 유지
MAJOR → 하위 호환이 깨지는 큰 변경
```

**② 문서 생성**

```bash
./generate_docs.sh
```

`VERSION` 파일의 번호가 Doxyfile에 자동 주입되어 HTML 헤더에 반영됩니다.

**③ README.md 변경 이력 업데이트**

```markdown
| 2025-03-15 | v1.1.0 | 기능 추가 내용 | 홍길동 |
```

**④ Git 커밋 및 태그**

```bash
git add .
```

## 7. 프레임워크별 적용 가이드

이 시스템에서 프레임워크에 따라 달라지는 항목은 세 가지입니다.

| 항목 | 위치 |
|---|---|
| 소스 폴더 경로 | Doxyfile `INPUT` |
| 제외 경로 | Doxyfile `EXCLUDE_PATTERNS` |
| 빌드 명령어 | `README.md` Quick Start, `mainpage.dox` |

나머지(주석 문법, 태그, 스크립트, `.dox` 파일 작성법)는 모두 동일합니다.

---

### ESP-IDF (ESP32)

```ini
# Doxyfile
INPUT            = main/ Docs/
EXCLUDE_PATTERNS = */build/* */managed_components/*
```

```bash
# README Quick Start
idf.py build flash monitor
```

> `managed_components/`는 반드시 제외해야 합니다. Espressif 라이브러리 전체가 파싱되어 문서가 수천 페이지로 불어납니다.

---

### Arduino

```ini
# Doxyfile
INPUT            = src/ Docs/
EXCLUDE_PATTERNS = */build/* */libraries/*
```

```bash
# README Quick Start
arduino-cli compile --fqbn arduino:avr:uno .
arduino-cli upload -p /dev/ttyUSB0 --fqbn arduino:avr:uno .
```

> Arduino 프로젝트는 `.ino` 파일이 진입점입니다. `FILE_PATTERNS`에 `*.ino`를 추가하세요.

```ini
FILE_PATTERNS = *.c *.cpp *.h *.ino *.dox
```

---

### STM32 HAL (CubeMX 기준)

CubeMX로 생성한 프로젝트는 빌드 시스템(CubeIDE, CMake, Makefile)에 관계없이 폴더 구조가 동일합니다.

```ini
# Doxyfile
INPUT            = Core/Src/ Core/Inc/ Docs/
EXCLUDE_PATTERNS = */build/* */Drivers/* */Middlewares/*
```

> `Drivers/`와 `Middlewares/`는 CubeMX가 자동 생성하는 HAL/BSP 코드입니다. 반드시 제외하세요.

---

### 순수 C/C++ (CMake / Makefile)

```ini
# Doxyfile
INPUT            = src/ include/ Docs/
EXCLUDE_PATTERNS = */build/* */third_party/* */vendor/*
```

```bash
# README Quick Start (CMake)
cmake -B build && cmake --build build

# README Quick Start (Makefile)
make
```

---

### 프레임워크별 변경 항목 요약

| 프레임워크 | INPUT | 주요 EXCLUDE_PATTERNS | FILE_PATTERNS 추가 |
|---|---|---|---|
| ESP-IDF | `main/ Docs/` | `*/managed_components/*` | 없음 |
| Arduino | `src/ Docs/` | `*/libraries/*` | `*.ino` |
| STM32 HAL (CubeMX) | `Core/Src/ Core/Inc/ Docs/` | `*/Drivers/* */Middlewares/*` | 없음 |
| 순수 C/C++ | `src/ include/ Docs/` | `*/third_party/* */vendor/*` | 없음 |
